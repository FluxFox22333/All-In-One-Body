# Fivefold 0.3.2-alpha：A/D 输入回归修复尝试

目标：Minecraft Java 26.3 / NeoForge 26.3.0.39-beta / Java 25。
所有客户端与服务器一起升级；网络协议为6，不能混装旧版。

## 判断与证据

本次读取四份版本说明，并对比上传的0.1.0、0.2.0、0.2.1、0.3.0、0.3.1 JAR。找回的0.3.1源码所对应编译目录中，所有class均与上传的0.3.1 JAR逐字节一致。

**确认了代码缺陷，但尚未在真实多人游戏中复现你报告的延迟，不能宣称已找出全部原因。**

| 项目 | 旧版/0.3.1行为 | 本次处理 |
|---|---|---|
| 身体窗口失焦 | 0.3.1的applyMovement把窗口焦点用于整个移动合并结果；身体窗口失焦，队友A/D也被清零。旧版没有这项整体移动门控 | 焦点只限制身体本人的输入；游戏界面允许移动时仍执行队友有效输入 |
| 多人共用同键 | 0.3.1加入otherHeld排除身体本人的输入，但即时转发仍只比较全队合并值；全队按住状态不变时，队友单独按下/松开的变化漏转发 | 同时比较全队输入和队友输入，任一变化即转发 |
| 本地疾跑 | 移动使用即时合并值，但aiStep末尾仍依据旧merged回包取消疾跑 | 疾跑停止判断统一读取当前有效移动输入 |
| 状态同步 | 状态包使权限/界面条件重新匹配后，原先要等其他回调再刷新移动键 | 收到状态包立即刷新 |
| 房间/权限切换 | 普通输入未校验房间和权限版本；frame缺少房间标识 | 添加并校验标识，拒绝不匹配输入 |

第二项通常只在身体与队友共用同键时出现；默认五人分别控制A/D时，不应将它当作唯一解释。漏转发会等待下一次服务器tick补发，正常20TPS下该处额外等待约0～50毫秒，不是实测总延迟。

第一项只修复“失焦本身”造成的阻断。如果游戏自动弹出暂停菜单、身体打开F8/F10等本地菜单，或后台帧率变低，仍可能停止/拖慢执行；本版保留原有菜单停止行为。失焦成员自己的按键会被释放。

各版本按键发生变化时本来就会立即调用sendInput，不能说旧版只每秒发送20次按键变化。20Hz是游戏刻续期频率。0.3.1本地即时合并只作用于身体原主人，不代表其他成员也有移动位置预测。

## 仍然存在的移动链路

队友按键 → 服务器合并 → 身体客户端模拟移动 → 服务器同步位置 → 队友看到移动。

0.3.2没有改变身体物理模拟归属，也没有引入远程位置预测。鼠标负责人转头可以本地预测，而同一人按A/D仍要等待这条位置链路，所以转头流畅不等于横移零延迟。该链路在早期版本也存在，不能仅凭它证明0.3.1比0.2.0更慢。

若所有窗口正常聚焦、身体没有本地菜单、各人独占按键时，仍出现明显持续延迟，本次已定位的条件不能完整解释该现象，仍需实际联机采样定位。

## 安装

1. 退出游戏，停止专用服务器。
2. 所有客户端和服务器删除旧Fivefold JAR，仅保留fivefold-0.3.2-alpha.jar。
3. 重新启动，重新创建房间。继续使用原分工即可。

0.3.1的原版容器背景修复及视角功能保留；人数范围仍为2～32人。

## 建议先测试这几项

在相同世界、相同网络、相同分工下与0.3.1比较，避免一边改变环境一边比较版本。

1. 身体玩家在游戏画面中，队友分别短按A/D、长按、松开、交替横移。分别看身体端是否及时移动、按键者是否晚看到移动。
2. 身体窗口失焦但不打开暂停/本地菜单时，队友继续操作A/D；身体本人原来按住的键不应继续保持。后台限帧会干扰比较。
3. 将同一移动键给身体和一名队友：两人按住，队友先松，身体再松；以及相反顺序。身体应仅在最后一人松开时停止。
4. 测试允许的疾跑组合、A+D同时按下、背包开关、权限修改、F8/F10、断线释放。

如果A/D仍慢，最有价值的反馈是：A/D由身体本人还是队友操作；身体端是否也晚动；是否同机多开/切换窗口；延迟主要在按下、松开还是整个移动过程中。最好同时录下身体端与按键端，并记录双方Ping及服务器TPS。

## 验证范围

- 使用现有精确目标版本API完成Java 25编译。
- 43项纯Java测试全部通过：原有35项加8项输入回归测试。
- 新测试覆盖失焦时保留队友A/D、释放身体本地输入、停用门控、A/D抵消所需的双按键状态、同键持有者变化及时转发、心跳去重及即时疾跑输入。
- 本次没有运行真实多人会话、游戏内Mixin加载验收或延迟/帧率测量。算法测试不等于整机联机验收。
- 未调整UI渲染或位置插值，没有通过扩大插值缓冲掩盖移动延迟。
