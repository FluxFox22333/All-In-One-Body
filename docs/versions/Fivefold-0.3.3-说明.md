# Fivefold 0.3.3-alpha：身体端视角与移动链路修复

适用：Minecraft Java 26.3 / NeoForge 26.3.0.39-beta / Java 25。
协议版本7。所有客户端和专用服务器必须一起更换；不能混用旧版。

## 本次针对的反馈

别人操作鼠标时，身体原主人看起来明显卡顿，操作者自己却流畅；A/D测试中，身体端本身也晚动。

0.3.2只修了焦点、同键共享、疾跑状态等输入边界，没有解决这个反馈所指的主要链路。本次修改如下。

## 原因分析

1. 操作者本地逐帧应用鼠标输入，身体端等待收到角度。0.3.1/0.3.2专门绕过了身体端的视角过渡，并将实体上一帧角度直接覆盖成当前角度，因此身体观看直接跳到收到的角度。这是源码确认的阶梯式画面来源。
2. 旧版Wire处理注册在服务器主线程。即使客户端约60批/秒发送视角，服务器主线程的处理时机仍可能让多个更新集中到达。队友移动也先等这条主线程处理链，再转到身体端执行。
3. 身体端也晚动，说明不能仅归因于旁观者的远程位置插值。0.3.2对失焦的修复并不足以覆盖正常聚焦时的这个现象。

以上是代码链路分析，不是你电脑上的实测延迟分解；不能据此声称网络、客户端帧率或服务器负载没有影响。

## 0.3.3的改动

| 环节 | 本版处理 |
|---|---|
| 队友持续移动输入 | 服务器网络处理阶段按已发布的权限快照合并并直接发往身体端，按下和松开不等待主线程的定时转发 |
| 队友视角输入 | 在独立、加锁的纯控制状态中按顺序合并，直接广播角度与确认序号；服务器实体角度在主线程应用 |
| 身体客户端 | 移动读取新通道；旧动作回包不能覆盖它，实时包按序号去重，过期包停止生效 |
| 身体观看视角 | 没有鼠标权限时，与其他非操作者一样逐帧过渡；本版过渡参数为20毫秒 |
| 鼠标操作者 | 保留本地逐帧预测与服务器确认，自己的视角不经过上述观看过渡 |
| 移动与画面分离 | 实际身体朝向用最新确认/预测角度；20毫秒仅作用于摄像机绘制，不用于延迟A/D或碰撞计算 |
| 心跳 | 相同状态的续期被合并；按键边沿仍立即转发，避免人数增加后每个心跳都额外广播 |
| 权限、菜单、重生与退出 | 校验房间、权限版本和控制代次；失效时清除旧输入；开关共享菜单重置视角代次，避免重放未确认的旧转头 |
| 物品与界面 | 背包、攻击/使用事件、容器点击等仍在原有主线程流程处理；保留之前的UI背景修复 |

网络线程不直接操作世界、实体、背包、容器或可变的房间成员表。它只读主线程发布的不可变配置，并操作受同一锁保护的控制状态。客户端收到数据后仍在客户端主线程应用。

## 仍然存在的延迟和取舍

- 队友输入仍需经过“操作者→服务器→身体端”的网络传输，身体位置物理仍按客户端游戏刻执行。
- 20毫秒是摄像机过渡参数，不是总延迟，也不是实测节省值。画面朝向在转动中可短暂落后于实际移动朝向，参数比0.3.0的50毫秒更短。
- 不预测未来鼠标输入，不承诺身体观看能达到操作者本地输入完全相同的响应。网络成批到包时仍可能有顿挫。
- 没有加入队友移动位置预测，旁观位置链路仍需原版同步。
- 身体打开F8/F10等本地菜单仍会停止其执行移动；身体客户端后台低帧率仍可能拖慢模拟。
- 这次涉及网络线程与主线程分工，尚未进行真实多人运行验收，属于需要联机验证的Alpha修复版。

## 安装与复测

1. 所有人退出游戏，停止专用服务器。
2. 所有客户端和服务器删除旧Fivefold JAR，仅放入fivefold-0.3.3-alpha.jar。
3. 启动后重新建房，恢复原分工。
4. 先让身体原主人不持有鼠标权限，由队友缓慢左右转头、快速转头、突然停下。观察身体端是否仍然明显一格一格跳动。
5. 队友短按A、短按D、交替按、长按后松开；重点观察身体端的开始和停止，再看操作者端。
6. 连续转头时横移，并复测同键多人持有、F8权限切换、背包开关和离开/重连。

F8为分工设置，F10为个人本地菜单；2～32人分工及原版容器支持范围与此前一致。

若仍然延迟，请优先提供同一次操作的身体端与操作者端录像，以及双方Ping、身体端FPS、服务器TPS。需要区分转头画面顿挫和身体位置实际晚动，不能只以操作者自己的转头流畅度判断整条链路。

## 已完成的验证

- 全部源码使用精确目标版本API，以Java 25编译通过。
- 60项JUnit逻辑/并发测试全部通过；新增17项覆盖即时控制、权限隔离、时间超时、顺序、重置、双线程视角合并、旧包不能撤销松键、20毫秒过渡与实际角度分离。
- 测试可在不推进服务器游戏刻的条件下接收并合并移动与连续60次视角更新，验证新控制逻辑不依赖服务器tick推进。这不是游戏内60Hz实测。
- 核对目标版本Connection.send的网络线程投递路径，以及NeoForge的NETWORK注册和enqueueWork接口。
- 未完成真实游戏启动/多人会话、网络吞吐和延迟测量、GUI画面验收或32人压力测试。
